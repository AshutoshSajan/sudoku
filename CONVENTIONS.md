# Conventions — Sudoku (Flutter)

**Canonical rule book for how this repo is run.** `README.md` keeps only
product facts; this file owns process. Agents load `AGENTS.md` (hard rules,
self-sufficient) → `CLAUDE.md` imports it; this file is the depth layer.

---

## 1. Two-trunk branch model

Exactly two trunks exist. There are no other tiers (no staging, no sandbox,
no nightly branches — those tier names are retired).

| Trunk | Meaning | Receives |
|-------|---------|----------|
| `dev` | integration trunk | PR merges from task branches |
| `main` | deployable trunk | PR merges from `dev` (release PRs); tags `vX.Y.Z` |

```
feat/* fix/* chore/* … ──PR──▶ dev ──release PR──▶ main ──tag──▶ release
```

- Task branches are cut **only from `origin/dev`** and PR'd **into `dev`**:
  `gh pr create --base dev`.
- Allowed prefixes (`feat/`, `fix/`, `chore/`, `ci/`, `docs/`, `perf/`,
  `refactor/`, `test/`, `release/`, `dependabot/*`). The retired
  `feature/*`, `bugfix/*`, `hotfix/*` naming is gone.
- `dev` → `main` happens through a **release PR** with **merge commits**
  (GitHub's "Create a merge commit"). Squash and rebase merges are
  forbidden on both trunks: every trunk head is a merge commit, and the
  guards (§4) fail anything else.
- Every change gets its own PR. One concern per PR — no mixing feature
  work with infrastructure or docs work.

## 2. Never-list (critical invariants)

Actions on this list are **not options** — they are not mistakes to apologize
for later, they simply are not taken:

- **Trunks are never worked on directly.** No local commits to `main`/`dev`,
  no pushes to them, no local merges pushed to them, no force-pushes into
  them (CI guard fails those), no resets, no deletions. All trunk movement
  goes through GitHub PR merges.
- **No history rewrites on shared branches** (`--force`, `git push --force-with-lease`
  on a collaborator-visible branch, moving tags that others build on).
- **No database deletion/destruction.** Never drop `*.db`/store files or
  tables, no `TRUNCATE`, no bulk deletes, no reversed migrations. Schema
  changes are additive only. (The app persists via `shared_preferences` —
  `_autosaveGame` key in `lib/services/game_storage.dart` — the rule covers
  any store, file, or table added later.)
- **No secrets in the repo.** Env files stay local; only `.env.example`-style
  templates are committed. Signing keys and store secrets (`ANDROID_*`)
  stay in repo Settings/secret storage; `.gitignore` already excludes
  `key.properties`, `*.keystore`, `*.jks`, `.env`.
- **Generated files are regenerated by tooling, never hand-edited:**
  `CHANGELOG.md` (git-cliff), `pubspec.lock` (`flutter pub get`),
  `gradle wrapper` outputs, `extension/app/` (built from the web build).
- **Hooks are bypassed only as a deliberate, stated exception.** `--no-verify`
  or the `SUDOKU_HOOK_GATE` contract-test override require saying so in the
  PR/comment, with the reason.
- **Actions that cannot be undone are not taken.** Force-pushes, deleting
  published GitHub Releases/tags (see the re-roll procedure instead),
  destructive commands against shared state.

## 3. Commits, changelog, checks

- [Conventional Commits](https://www.conventionalcommits.org/),
  enforced by `.githooks/commit-msg`. Types: `feat fix docs style
  refactor perf test build ci chore revert`. Merge commits are exempt.
- `CHANGELOG.md` is generated by git-cliff (`cliff.toml`) — never hand-edited.
  CI regenerates on `main`; `.githooks/post-merge` does it locally.
- **Verify before push:** `bash tool/verify.sh` (flutter analyze + flutter
  test — same as CI). `.githooks/pre-push` runs this gate and refuses
  trunk pushes. Hooks stay enabled per clone with:
  `git config core.hooksPath .githooks`
- CI-minute hygiene: keep runs cheap and failures isolated. Release
  dry-runs via the `platforms` input of Release, never a blind re-queue.

## 4. CI guards & automation (free-plan: every job is cheap)

| Workflow | Trigger | What it enforces |
|----------|---------|------------------|
| `guard-dev.yml` | push to `dev` | head is a merge commit (<2 parents fails — direct commits **and** squashes), no force, no deletion; read from the event payload with `jq`, no checkout |
| `guard-main.yml` | push to `main` | same armor for the deployable trunk |
| `prune-branch.yml` | PR into `dev`/`main` **closed & merged** | deletes the merged task branch — only allowlisted prefixes, never trunks, and only after `git merge-base --is-ancestor origin/<head> origin/<base>` proves the landing |
| `deps-audit.yml` | weekly cron + PRs into `main` touching `pubspec.yaml`/`pubspec.lock` | `osv-scanner scan --lockfile=pubspec.lock` (pinned by version **and** sha256, verified with `sha256sum -c -`), fails on findings with an upgrade hint — no SDK involved |
| `dependabot.yml` | weekly | `pub` + `github-actions` ecosystems, all PRs → `dev` |
| `ci.yaml` (existing) | push/PR `dev`+`main` | `actionlint` (with shellcheck), `verify` (analyze+test), changelog bot, extension publishes on `ext-v*` |

Dependabot PRs — like all PRs into `dev` — must be merged with
**Create a merge commit**, or `guard-dev` goes red.

## 5. Dependencies

- Ship only licenses compatible with the app's GPL-3.0-only; note the
  license when adding a package, run the audit.
- `pubspec.lock` is committed; audits and reproducible builds depend on it.
- Weekly: Dependabot PRs into `dev`; vulnerability gate `deps-audit.yml`.
- Local parity: `tool/deps.sh` (add `--offline` to skip all network work).

## 6. Release contract (unchanged; see also CONTRIBUTING pointer)

- Version truth is the tag: `vX.Y.Z` on `main`, injected via
  `--build-name/--build-number`; `snap/snapcraft.yaml` version must equal it.
- Tag the newest **merge commit without `[skip ci]`** in its message, never
  bare HEAD — the changelog bot's `[skip ci]` commit on `main` suppresses
  tag-push runs.
- Re-rolling a failed release: delete the published GitHub Release in the
  browser **first**, then move the tag (`git tag -f vX.Y.Z <merge-sha>`).
- `ext-v*` tags release extensions only; they never trigger app releases.
- Keys/signing secrets live outside the repo.

- `README.md` — product only (what it is, install, run/build/deploy).
- `CONVENTIONS.md` (this file) — process, branching, CI, release flow.
- `ROADMAP.md` — roadmap, todos, working notes (in-flight work status).
- `AGENTS.md` — self-sufficient hard rules loaded by agent harnesses;
  `CLAUDE.md` imports it (`@AGENTS.md`).

## 8. Working in shared checkouts

If another session/agent is working in a checkout, cut your work dir with
`git worktree add ../sudoku-<branch> <branch>` — never touch their
uncommitted files, never share a dirty tree.
